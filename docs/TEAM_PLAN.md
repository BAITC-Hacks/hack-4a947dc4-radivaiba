# Работа команды после получения общей версии

Все разработчики используют отдельные клоны. Интеграция идёт в codex/mvp, публикация в main — через проверенный PR. PostgreSQL-ветку сначала интегрируют в общую базу; дальнейшая работа не создаёт второе независимое хранилище.

| Время     | №1 — frontend                                   | №2 — backend и интеграция                         | №3 — алгоритм и AI                              |
| --------- | ----------------------------------------------- | ------------------------------------------------- | ----------------------------------------------- |
| 0:00–0:20 | Запуск, проверка новых экранов и языков         | Проверка БД, миграций, аккаунтов, резервной копии | Проверка модулей, EXP, режима AI                |
| 0:20–1:30 | Дерево, следующий шаг, отправка результата      | Транзакции, доступ к профилям/файлам, проверка HR | Персональная польза, первый шаг, реальные факты |
| 1:30–2:30 | HR-очередь, профиль, статусы и мобильная версия | Сквозной сценарий и устранение конфликтов         | Смена цели, повтор клуба, отсутствие кандидатов |
| 2:30–3:15 | Проверка доступности и ошибок                   | Интеграция веток, Go/PG/TS/build                  | Границы месяца, таймаут и неверный ответ AI     |
| 3:15–4:00 | Скриншоты синтетических профилей, демо          | Чистый запуск, README, backup/restore             | Краткое объяснение алгоритма жюри               |

Этот четырёхчасовой блок — доводка работающей общей версии. Полная разработка БД, индивидуальных аккаунтов, защищённых файлов, аудита, дерева и трёх языков с нуля не укладывается в четыре часа одним backend-разработчиком. Для новой функциональности оценивать задачи отдельно, сохраняя время на интеграцию и проверку.

## Владельцы файлов

- №1: frontend/src/pages, frontend/src/components, frontend/src/api, frontend/src/i18n, стили и React-конфигурация.
- №2: backend/internal/model, auth, httpapi, store и SQL-миграции; backend/cmd; contracts/openapi.yaml; scripts; Docker, compose, CI, README и docs.
- №3: backend/internal/engine, backend/internal/llm и их тесты. Расчёты дерева/EXP и рекомендации не дублируются на frontend.

Сначала №2 фиксирует контракт и SQL-границы, №1 обновляет TypeScript-типы, №3 согласует модель. №1 и №3 работают параллельно после этого. Новая миграция получает новый номер; старые применённые файлы не переписываются. Корневой lock-файл объединяет №2 после согласования frontend-зависимостей.

## Готовность изменения

1. Прикладной сценарий проходит целиком, включая ошибки и отказ доступа.
2. Изменения БД сохраняются после перезапуска, награда начисляется один раз.
3. Go, PostgreSQL, TypeScript и production-сборка проходят; при необходимости race detector в Linux.
4. Интерфейс проверен в браузере на desktop/mobile, с клавиатуры и reduced-motion.
5. Контракт, README и инструкция обновления соответствуют коду; не заявлены непроверенные результаты.
6. В коммите нет .env, датасета, паролей, доказательств и резервных копий.

После 3:15 новые функции не добавлять. Уведомления, SSO, редактор сложных заданий и несколько экземпляров сервера остаются следующими этапами.
